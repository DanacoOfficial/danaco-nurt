## The shape of the system

Danaco Nurt is a Cargo workspace. The manifest declares version 0.1.2, edition 2024, the minimum Rust version 1.98 and the license Apache-2.0, and every directory of `crates/` is a member. The workspace lint `unsafe_code` is set to `deny`. A crate that calls operating system interfaces opts out (`nurt-fs` does so at the head of its `lib.rs`), and the crate graph document requires a `// SAFETY:` comment on every `unsafe` block; `nurt-types`, for example, forbids unsafe code outright.

A program travels through the system in one direction. Text is parsed into a syntax tree, the tree is bound to the command catalog and checked, the plan is built, the executor runs the stages and passes records between them, the commands change the world through the journal, and the report describes the effects. The [engine](/architecture/engine/) page follows one program through these steps. The entry points do not implement the language themselves: the C interface, the protocol server, the command line interface and the integrations all call the same Rust facade, `Engine` of `nurt-core`.

## The layers

The table names the crates of each functional layer. The crate `nurt-contracts` sits under all of them and holds the shared contracts: syntax trees, records, errors, the stage interface, the report, the journal and the configuration. `nurt-types` holds the values and records of the language.

| Layer | Role | Crates |
|---|---|---|
| Language front end | lexer, parsers of the three notation variants, canonical printer, notation correction, help, migration of shell scripts | `nurt-syntax`, `nurt-correct`, `nurt-help`, `nurt-migrate` |
| Catalog, checker and planner | command registry, binding of syntax trees to the catalog, execution planning | `nurt-catalog`, `nurt-bind`, `nurt-plan` |
| Executor | streaming pipeline executor and record stages | `nurt-exec` |
| Command implementations | files, text, archives, notebooks, documents, source code, tests and analysis, programs and jobs, version control, system, network, schedules, installed programs, extensions | `nurt-files`, `nurt-text`, `nurt-archive`, `nurt-notebook`, `nurt-doc`, `nurt-code`, `nurt-lspclient`, `nurt-verify`, `nurt-proc`, `nurt-git`, `nurt-git-ops`, `nurt-git-transport`, `nurt-sys`, `nurt-syslog`, `nurt-net`, `nurt-sched`, `nurt-programs`, `nurt-ext` |
| Journal and file system | operation journal, free space for the journal, platform file system layer | `nurt-journal`, `nurt-space`, `nurt-fs` |
| Report | effect report model and renderers | `nurt-report` |
| Engine and service | engine facade, background service | `nurt-core`, `nurt-service` |
| Command line program | the `nurt` executable and the Rust interface of the product | `nurt-cli`, `nurt` |
| Model Context Protocol server | MCP tools and resources, definitions of the `nurt` tool | `nurt-mcp`, `nurt-tooldef` |
| Language server | diagnostics, completion and formatting of `.nurt` files | `nurt-langserver` |
| C interface and bindings | the C ABI and the Node.js addon; the other bindings are in `bindings/` | `nurt-ffi`, `nurt-node` |

The remaining crates are support and tools: `nurt-testkit`, `nurt-conformance`, `nurt-bench`, `nurt-git-difftest`, `nurt-crashfs`, `nurt-docgen` and the two vendored crates `jaq-json` and `nurt-pdf-extract`. The [crates](/architecture/crates/) page lists every crate with its description.

## Rules of the dependency graph

The allowed dependencies between workspace crates are data in `tables/crate-graph.toml`. The test `crates/nurt-contracts/tests/workspace_graph.rs` reads every manifest and fails when a crate declares a dependency that the table does not allow. The rules are written in [crate graph and visibility](/docs/architecture/crate-graph/):

- Every crate belongs to one of eight build layers, from the lowest: contract, foundation, base, library, component, host, interface and tool. A crate depends only on crates of the same or a lower layer, and the graph is acyclic.
- Every crate also belongs to an area: runtime, language, storage, files, structured, process, system, git or integration. Crates of different areas depend on each other only through shared crates such as `nurt-contracts`, `nurt-types`, `nurt-catalog`, `nurt-fs` and `nurt-journal`.
- A command that needs a capability of another area calls a service trait defined in `nurt-contracts`, and the host layer passes the implementation in. Changes to files go through the transaction interface of the journal, never around it.
- Only `nurt-ffi` exports C symbols, declared in `crates/nurt-ffi/include/nurt.h`.

<Callout type="note" title="A document that lags the table">
  The crate graph document of 0.1.2 still has a section "Reserved names" that calls `nurt-programs`, `nurt-tooldef`, `nurt-docgen`, `nurt-crashfs` and `nurt` planned crates. All five exist in `crates/` in version 0.1.2, and `tables/crate-graph.toml` has an entry for each of them without a reserved mark. The table is the authority.
</Callout>

## Repository layout

| Path | Content |
|---|---|
| `crates/` | Rust crates of the engine, the command line program and the libraries |
| `spec/` | specification: syntax tree, grammar, records, stages, report, journal, services, supervisor, configuration, errors, schemas |
| `catalog/` | command catalog: signatures and descriptions of commands |
| `docs/` | user and integrator documentation, reference, architecture and conventions |
| `tables/` | data tables used by the engine and its tests, among them `crate-graph.toml` |
| `tools/` | scripts for continuous integration and release |
| `bindings/` | bindings for Go, Node.js, .NET, Java and Python |
| `conformance/` | cases of the conformance suite run by `nurt-conformance` |
| `bench/` | tasks, oracles, fixtures and protocol of the benchmark |
| `packaging/` | packaging and release automation: `deb`, `rpm`, `homebrew`, `scoop`, `chocolatey`, `winget`, `release` and others |
| `editors/`, `integrations/` | editor support (TextMate grammar, tree-sitter grammar) and integrations (VS Code, containers, setup action, examples) |
| `examples/` | the C example `examples/c/hello.c` |
| `.github/workflows/` | continuous integration and release workflows |

The root also holds `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` (the pinned toolchain, 1.98.1), `deny.toml`, `CHANGELOG.md`, `SECURITY.md`, `NOTICE` and `LICENSE`. Building from source needs Rust through rustup and a C compiler, because SQLite and the tree-sitter grammars are compiled from source.
