## Language bindings

The directory `bindings/` holds clients for five languages. Each one offers the same API: run a program, check it, follow the events of an execution, cancel it. A language error is part of the response, and a failure of the call itself is an exception that carries the status of the C interface. The request types of all five carry `params`, `privilege` and `as_user` (CHANGELOG, 0.1.1).

| Language | Package | Backends |
|---|---|---|
| Python | `pip install nurt` | `library` through `ctypes`, `process` (`nurt serve --stdio`), `auto`; `AsyncNurt` for coroutines |
| TypeScript, Node.js | `npm install nurt` | `library` (Node-API addon), `process`, `auto`; Node.js 18 or later, Bun and Deno |
| Go | `go get github.com/DanacoOfficial/danaco-nurt/bindings/go` | `process` by default, pure Go; `library` through cgo with `-tags nurt_cgo` |
| Java | `pl.danaco-group:nurt`, and `nurt-ffm` for the library backend | `PROCESS` on Java 17 or later; `LIBRARY` through the Foreign Function and Memory API on Java 22 or later |
| .NET | `dotnet add package Danaco.Nurt` | `Library`, `Process`, `Auto`; .NET 8 and .NET Standard 2.0 |

The Python wheels, the Node platform packages and the Java and .NET packages carry the `nurt` executable and `libnurt` for Linux, macOS and Windows on x86-64 and ARM64, according to their READMEs. The Go module locates the executable through `ClientOptions.Executable`, `NURT_EXECUTABLE` or `PATH`. Each binding has tests that run against the engine when `NURT_TEST_EXECUTABLE` names it.

The release report of 27 November 2026 (release candidate of 0.1.1) records these checks against the program of the Linux glibc archive: Go (`go vet`, `go test -race`), Node (120 of 120 tests), .NET (105 passed, 12 skipped) and Java 21 (101 of 101). The same report lists the shared conformance cases of `conformance/bindings` as not passing in full against the engine (11 of 29 fail), because the case data differ from the engine; for example `history.entries` expects `entries`, where the protocol reference documents `operations`. That case data is unchanged in the 0.1.2 tree, and no report of a run of 0.1.2 exists. A short example from the Python README:

```python
from nurt import Nurt

with Nurt() as nurt:
    response = nurt.run('find "/home/user/project" glob: "**/*.py"', limit=20)
    if response.ok:
        print(response.text)
    else:
        print(response.error["code"], response.error.get("fix"))
```

## The C interface

`libnurt` (crate `nurt-ffi`) exposes the engine to every language with a C foreign function interface, through `nurt.h`. Strings are UTF-8, complex values are JSON documents in the published formats, and handles are opaque. `nurt_status` reports only failures of the call; errors of the language come back with `NURT_OK` inside the JSON result. Within a major version the interface only grows, and a caller passes `NURT_ABI_VERSION` to `nurt_abi_check` once after loading the library. Events of an execution reach a callback `nurt_event_cb`. The shared library is `libnurt.so.1` on Linux, `libnurt.1.dylib` on macOS and `nurt.dll` on Windows; on musl targets the archive holds the static `libnurt.a`, which must not be linked into one program with another static library written in Rust. See the [reference](/docs/reference/c-abi/) and the [architecture page](/docs/architecture/c-interface/).

## Language server and editors

`nurt lsp` serves the language protocol for `.nurt` files over standard input and output; a build without the component ends the command with exit code 3. The extension for Visual Studio Code in `integrations/vscode` uses it:

| Feature | Provided by |
|---|---|
| Syntax highlighting | TextMate grammar `source.nurt`, kept in `editors/textmate/nurt.tmLanguage.json` |
| Diagnostics, completion | `nurt lsp` |
| Commands | Run File (`nurt script`), Format File (`nurt fmt`), Restart Language Server |
| Settings | `nurt.path`, `nurt.lsp.enabled`, `nurt.trace.server` |

The extension does not install `nurt`, collects no telemetry and starts neither the language server nor a run in an untrusted workspace. The workflow `ci/vscode.yml` is defined to publish it to the Visual Studio Marketplace and to Open VSX; this page does not claim that it is published. The directory `editors/tree-sitter-nurt` holds Tree-sitter grammars with highlight and injection queries, three variants of the syntax (the package is marked private); it has no README, so the page states only what its `package.json` declares.

## Model Context Protocol and agent frameworks

`nurt mcp` serves the tool over the Model Context Protocol. The directory `integrations/examples` holds minimal agent loops for the Anthropic SDK (Python and TypeScript), the OpenAI SDK (Chat Completions and Responses), the Google Gen AI SDK, the Vercel AI SDK, LangGraph, Semantic Kernel, OpenHands and SWE-agent (which calls `nurt exec`), and client configurations for MCP clients. Their tests replace the model and the console with mock objects and need no keys. See [Nurt for AI agents](/product/ai-agents/).

## Extensions

Extensions add commands, document formats and grammars without changing the program. An extension is a directory with a manifest `nurt-ext.toml` and a WebAssembly component; a WebAssembly extension runs in a sandbox and reaches files only within the `permissions.read` and `permissions.write` that it declares. Native libraries are allowed only with the configuration key `ext.native` (off by default) and in builds with the `native` feature. Installation does not verify a signature or a checksum of the source. See the [extensions reference](/docs/reference/extensions/).

## Continuous integration and containers

| Integration | What it does |
|---|---|
| `setup-nurt` | a GitHub Action that installs Danaco Nurt, adds it to `PATH` and verifies the SHA-256 digest; Linux, macOS and Windows runners |
| devcontainer Feature | `ghcr.io/danacoofficial/features/nurt:1` installs the musl archive into `/usr/local/bin` on Debian, Ubuntu, Alpine and Red Hat based images |
| container images | `nurt`, `nurt-ci` and `nurt-devcontainer` for `linux/amd64` and `linux/arm64` |

The workflows in `.github/workflows` are examples of use, for instance [bindings-python.yml](https://github.com/DanacoOfficial/danaco-nurt/blob/release-0.1.2/.github/workflows/bindings-python.yml), [integrations-setup-nurt.yml](https://github.com/DanacoOfficial/danaco-nurt/blob/release-0.1.2/.github/workflows/integrations-setup-nurt.yml) and [integrations-containers.yml](https://github.com/DanacoOfficial/danaco-nurt/blob/release-0.1.2/.github/workflows/integrations-containers.yml). A workflow step that uses the action:

```yaml
steps:
  - uses: DanacoOfficial/setup-nurt@v1
    with:
      version: '1'
  - run: nurt version
```

<Callout type="note" title="Check the version you use">
  The library interfaces may change between 0.x versions, and the bindings pin the major version of the formats they use. The integrations that download release archives depend on the archives of a published release; the prepared release 0.1.2 contains no macOS archive. Platform limits are on the [platforms](/product/platforms/) page.
</Callout>
