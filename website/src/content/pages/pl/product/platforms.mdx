## Co jest dostarczane

<Stats>
  <Fact id="platforms" />
</Stats>

Danaco Nurt to jeden plik wykonywalny dla każdego systemu operacyjnego: `nurt` w systemach Linux i macOS, `nurt.exe` w systemie Windows. Strona instalacji stwierdza, że plik wykonywalny nie ma zależności w czasie działania. Dla systemu Linux README podaje dokładny sposób łączenia każdej kompilacji:

| Kompilacja dla Linuksa | Łączenie |
|---|---|
| glibc | łączy dynamicznie `libc.so.6`, `libm.so.6` i `libgcc_s.so.1`; pakiety `.deb` i `.rpm` je deklarują |
| musl | łączona statycznie |

Od 0.1.1 kompilacja glibc łączy liblzma statycznie, więc działa w systemie bez `liblzma.so.5` (dziennik zmian, 0.1.1). Skrypt `tools/ci/check-dependencies.sh` kończy się niepowodzeniem, gdy plik ELF wymienia bibliotekę współdzieloną spoza zestawu `libc.so.6`, `libm.so.6`, `libgcc_s.so.1` i dynamicznego ładowacza; kontrola plików Windows jest w skrypcie zarezerwowana i niezaimplementowana. Osobne archiwum zawiera bibliotekę C (`libnurt.so.1`, `libnurt.1.dylib` lub `nurt.dll`, wraz z `nurt.h`) dla celów, które ją mają; dla celów musl zawiera ono statyczną `libnurt.a`. Instalatory instalują wyłącznie archiwum programu. Szczegóły: [instalacja](/docs/guide/installation/).

## Obsługiwane systemy i archiwa

Strona instalacji i strona wersjonowania podają to samo wsparcie: Linux, macOS i Windows, każdy na architekturach x86_64 i aarch64 ([wersjonowanie i wsparcie](/docs/guide/versioning/)). Definicje pakietów nazywają archiwa `nurt-<version>-<target>` dla tych celów:

| Cel | Archiwum |
|---|---|
| `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` | `.tar.gz` |
| `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` | `.tar.gz` |
| `x86_64-apple-darwin`, `aarch64-apple-darwin` | `.tar.gz` |
| `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc` | `.zip` |

Każde wydanie publikuje `checksums.txt` z sumami SHA-256 i podpis odłączony `checksums.txt.asc`. Archiwum programu dla Linuksa i macOS zawiera `nurt`, teksty licencji, strony podręcznika, skrypty uzupełniania oraz dokumentację jako witrynę działającą bez sieci; archiwum dla Windows zawiera `nurt.exe`, teksty licencji, skrypty uzupełniania i dokumentację. Skrypt `tools/release/build-release.sh` buduje archiwa dla sześciu celów: czterech celów linuksowych (dwóch aarch64, gdy dostępny jest zig) i dwóch celów Windows.

<Callout type="warning" title="macOS w wydaniu 0.1.2">
  Dziennik zmian 0.1.2 stwierdza, że dla tego wydania nie jest publikowane żadne archiwum macOS; skrypt budujący nie ma celu macOS, więc archiwa macOS, które nazywają definicje pakietów, nie wchodzą w jego skład. Wydanie naprawia cztery usterki macOS: dziennik był nieaktywny na woluminie danych (`/System/Volumes/Data`), `max_memory` powodowało błąd `EINVAL` przy każdym uruchomieniu programu, lista członków grupy była odczytywana z niebezpiecznym założeniem o wyrównaniu, a wstrzymanie, wznowienie lub zatrzymanie programu, którego grupa procesów już się zakończyła, kończyło się błędem `EPERM`. Wymienia też znany problem: testy śledzenia zmian w `nurt-proc` i jeden test protokołu w `nurt-service` zawodzą sporadycznie na runnerach macOS ciągłej integracji, a przyczyna nie jest ustalona. Dla 0.1.1 raport z 27 listopada 2026 stwierdza, że `cargo check` przechodzi dla obu celów macOS; raportu z uruchomienia 0.1.2 nie ma. Traktuj macOS jako platformę, która ma zadania na runnerach macOS ciągłej integracji (`ci.yml`), a nie jako platformę z wydanym archiwum.
</Callout>

Mierzone liczby, które pojawiają się w innych miejscach witryny, pochodzą z uruchomienia kandydata na wydanie 0.1.1 z 27 listopada 2026: 12 archiwów dla sześciu celów oraz testy Windows na Windows 11 (zobacz [testowanie](/pl/quality/testing/)).

## Instalatory

| | `install.sh` (Linux, macOS) | `install.ps1` (Windows) |
|---|---|---|
| Polecenie | `curl -fsSL https://nurt.danaco-group.pl/install.sh \| sh` | `irm https://nurt.danaco-group.pl/install.ps1 \| iex` |
| Domyślny cel | `$HOME/.local/bin`, bez uprawnień | `%LOCALAPPDATA%\Programs\Nurt\bin`, bez praw administratora |
| Dla całego systemu | uruchomienie jako root z `--bin-dir /usr/local/bin` | `NURT_SCOPE=machine` z terminala administratora, do `%ProgramFiles%\Nurt` |
| `PATH` | bez zmian; skrypt zgłasza, gdy katalog nie jest w `PATH` | katalog dodawany do `PATH` użytkownika, a dla `machine` — do `PATH` komputera; `NURT_NO_PATH_UPDATE=1` pozostawia go bez zmian |
| Weryfikacja | SHA-256 archiwum względem `checksums.txt` | SHA-256 archiwum względem `checksums.txt` |
| Podpis | `--public-key` z `gpg` weryfikuje `checksums.txt.asc` | nieopisany w nagłówku skryptu |

`install.sh` w systemie Linux bierze statyczne archiwum musl, gdy wydanie je zawiera, a w przeciwnym razie archiwum glibc; maszyna z musl bierze wyłącznie archiwum musl. Oba skrypty czytają `NURT_VERSION` i `NURT_INSTALL_DIR`, a także `NURT_RELEASES_URL` dla innej lokalizacji wydań ([README pakietów](https://github.com/DanacoOfficial/danaco-nurt/blob/release-0.1.2/packaging/README.md)). `nurt.exe` nie żąda podniesienia uprawnień: jego manifest deklaruje poziom `asInvoker`.

## Pakiety

Katalog `packaging/` zawiera definicje; `render.py` wypełnia szablony skrótami z `checksums.txt`.

| Pakiet | Polecenie | Definicja |
|---|---|---|
| Debian, Ubuntu | `apt install nurt` po dodaniu repozytorium | `build-deb.sh` buduje `nurt`, `libnurt1` i `libnurt-dev`; `apt-repo/mkrepo.py` generuje repozytorium |
| Fedora, RHEL | `dnf install nurt` | `rpm/nurt.spec.in` dla `nurt`, `libnurt`, `libnurt-devel` |
| macOS, Linux | `brew install DanacoOfficial/tap/nurt` | formuła z archiwów wydania; druga formuła buduje ze źródeł |
| Windows | `winget install Danaco.Nurt` | przenośny plik zip, x64 i arm64 |
| Windows | `scoop install nurt` | manifest z `checkver` i `autoupdate` |
| Windows | `choco install nurt` | `nurt.nuspec.in` |

Katalog pakietów pokazuje definicje oraz workflow `release.yml`, który publikuje je przy użyciu swoich sekretów. Nie pokazuje, że 0.1.2 zostało opublikowane w którymkolwiek z tych kanałów; wydanie jest przygotowane, więc przed poleganiem na poleceniu potwierdź jego dostępność.

## Kontenery i CI

W `integrations/containers` zdefiniowano trzy obrazy: `ghcr.io/danacoofficial/nurt` (baza `scratch`, bez `git`, bez pakietu certyfikatów CA), `nurt-ci` (Debian bookworm slim z `git` i `ca-certificates`) oraz `nurt-devcontainer`. Wszystkie są budowane dla `linux/amd64` i `linux/arm64`, a `NURT_STATE_DIR` to `/var/lib/nurt`; zamontuj tam wolumin, aby zachować dziennik między kontenerami. Akcja GitHub `setup-nurt` działa na runnerach Linux, macOS i Windows i domyślnie weryfikuje skrót SHA-256; dla Linuksa pobiera archiwum musl. Zobacz [integracje](/pl/product/integrations/).

## Co jest niedostępne i gdzie

| Platforma | Ograniczenie | Źródło |
|---|---|---|
| macOS | dla 0.1.2 nie jest publikowane żadne archiwum; w 0.1.2 naprawiono cztery usterki; sporadyczne porażki testów na runnerach CI | CHANGELOG 0.1.2 |
| Windows | dostawca rejestru i `windows.cim` istnieją tylko tutaj; `create` potoku nazwanego lub węzła urządzenia kończy się błędem `E_OS_ONLY` | przewodnik dla Windows, CHANGELOG 0.1.1 |
| Windows | certyfikat podpisujący `nurt.exe` wystawił sam Danaco Holding Group Sp. z o.o., więc Windows zgłasza wydawcę jako niezweryfikowanego | CHANGELOG 0.1.0 |
| Linux, macOS | usługi to jednostki systemd i zadania launchd; `package.install` używa `apt`, `dnf`, `pacman`, `zypper` lub `brew` | [przewodnik dla Uniksa](/docs/guides/unix/) |
| wszystkie | rozszerzenia natywne ładują się tylko z `ext.native` i w kompilacjach z funkcją `native`; dziennik zmian 0.1.0 wymienia je jako niedostępne | [opis rozszerzeń](/docs/reference/extensions/) |
| wszystkie | zmiany na woluminach przechowywanych w pamięci, takich jak `tmpfs`, są raportowane jako nieodwracalne; dziennik jest tam nieaktywny | CHANGELOG 0.1.0 i 0.1.1 |

Dokumentację ścieżek i usług w każdym systemie opisują przewodniki dla systemów [Unix](/docs/guides/unix/) i [Windows](/docs/guides/windows/). Stan wydania przedstawia strona o [stanie projektu](/pl/project/status/).
