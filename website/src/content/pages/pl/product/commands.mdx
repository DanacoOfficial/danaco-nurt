## Czym jest katalog

Katalog poleceń jest jedynym źródłem sygnatur poleceń. Według [specyfikacji katalogu](/docs/specification/catalog/) czytają go wiązanie, wbudowana pomoc, opis dla modelu, dokumentacja referencyjna, definicje narzędzi i zestaw zgodności. Składa się z plików TOML w formacie `nurt-catalog/1`: `core.toml` dla poleceń rdzenia, jednego pliku dla każdej opcjonalnej grupy oraz indeksu (`_index.toml`), który wymienia pliki i oczekiwaną liczbę poleceń.

Wpis każdego polecenia podaje jego nazwę, kategorię (`source`, `transform`, `check`, `change`, `run`, `system`, `journal` lub `help`), odwracalność (`read`, `reversible`, `reversible_if_preserved` lub `irreversible`), rodzaje rekordów wejścia i wyjścia oraz parametry z typem, pozycją, wartością domyślną i streszczeniem. Polecenie może być ograniczone do niektórych systemów operacyjnych; w innym systemie wiązanie kończy się błędem `E_OS_ONLY`.

```toml
[[command]]
name = "set"
category = "change"
reversibility = "reversible"
effect = "local"
implementation = "builtin"
input = ["none", "entry"]
output = ["effect"]
summary = "Set values at key paths, preserving layout."
```

Wpis pochodzi ze specyfikacji katalogu. Zmiany wykonane przez polecenie są zapisywane w [dzienniku](/pl/product/journal-and-undo/) zgodnie z podaną tu odwracalnością.

## Polecenia rdzenia i opcjonalne grupy

34 polecenia rdzenia są zawsze opisywane modelowi. Obejmują pliki (`list`, `find`, `info`, `read`, `lines`, `write`, `copy`, `move`, `remove`, `rename`, `create`, `attributes`), tekst (`search`, `replace`, `insert`, `edit`), rekordy (`filter`, `select`, `sort`, `first`, `last`, `skip`, `count`), kontrole (`assert`, `verify`), programy (`run`, `jobs`, `stop`, `retry`), dziennik (`history`, `undo`, `redo`), kontynuację skróconej odpowiedzi (`next`) oraz `help`. Pozostałe polecenia należą do opcjonalnych grup, opisywanych na żądanie. Poniższe liczby pochodzą z `catalog/_index.toml`.

## Jak zbudowana jest strona polecenia

Każde polecenie katalogu ma jedną stronę i każda strona należy do polecenia. Strona ma stałą kolejność sekcji, określoną w [konwencjach dokumentacji poleceń](/docs/commands/):

| Sekcja | Źródło |
|---|---|
| Synopsis | generowana z katalogu |
| Description | pisana ręcznie |
| Parameters (nazwa, typ, wartość domyślna, opis) | generowana, opisy można rozszerzać |
| Input and output | generowana |
| Effect (kategoria, odwracalność i jej warunki) | generowana, uwagi pisane ręcznie |
| Examples (co najmniej trzy) | pisane ręcznie |
| Errors i Related | pisane ręcznie |

Pierwsze trzy przykłady to te, które pokazuje `help <command>`.

## Jak kompilacja sprawdza strony

Kompilacja dokumentacji kończy się niepowodzeniem, gdy:

- polecenie nie ma strony albo strona nie ma polecenia;
- front matter (`command`, `group`, `summary`) różni się od katalogu;
- sekcja generowana różni się od tekstu wygenerowanego z katalogu;
- strona ma mniej niż trzy bloki `nurt example`;
- przykład nie daje się przeanalizować, nie wiąże się, nie uruchamia się na wirtualnym systemie plików albo jego wynik nie zawiera oczekiwanego fragmentu;
- nazwa polecenia lub parametru w odwrotnych apostrofach nie istnieje w katalogu.

Sam katalog jest sprawdzany przez zestaw testów, który wymaga braku problemów w każdym pliku `catalog/`. Wśród kontroli: nazwy są poprawne i niepowtarzalne, każde wyrażenie typu daje się przeanalizować, parametr wymagany nie ma wartości domyślnej, a indeks wymienia każdy plik z właściwą liczbą poleceń, sumującą się do `total`.

## Jak sprawdzane są nazwy, parametry i typy

Wiązanie działa przed jakimkolwiek skutkiem. Program, który nie może być poprawny, jest odrzucany kodem nazywającym problem, a błąd wymienia najbliższe nazwy lub dopuszczalne typy.

| Kod | Problem |
|---|---|
| `E_UNKNOWN_COMMAND`, `E_UNKNOWN_PARAM` | nieznana nazwa; `expected` wymienia do ośmiu najbliższych nazw |
| `E_MISSING_PARAM` | brakuje parametru wymaganego |
| `E_PARAM_CONFLICT` | podano razem parametry, które się wykluczają |
| `E_TYPE` | wartość lub strumień rekordów ma typ, którego to miejsce nie przyjmuje |
| `E_UNKNOWN_VALUE` | wartość wyliczenia, która nie istnieje |

Typy zapisuje się jako wyrażenia, takie jak `path | list<path>`, `enum(report|force|abort)` czy `stream<entry>`. Tekst w cudzysłowie jest w miejscu danego typu przekształcany na `path`, `glob`, `instant`, `key`, `size` lub `duration`. Każde związane drzewo zapisuje `catalog_rev`, czyli SHA-256 kanonicznego katalogu, więc każda zmiana polecenia, parametru lub opisu zmienia rewizję.

<Callout type="warning" title="Katalog może się zmieniać między wersjami 0.x">
  W ramach `nurt-catalog/1` katalog tylko rośnie: nowe polecenia, parametry opcjonalne, wartości wyliczeń i klucze. Usunięcie lub zmiana nazwy polecenia albo niezgodna zmiana typu jest zmianą wersji głównej. W wersjach 0.x dziennik zmian ostrzega, że katalog może się zmieniać.
</Callout>
